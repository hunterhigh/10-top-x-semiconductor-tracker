# 1. 产品目标与信息架构

## 1.1 产品目标

- 状态：`已确认`
- 责任方：产品 / 前端 / 后端共同遵守

Dashboard 的目标是帮助用户快速发现：10 个市场账号当天、当周及滚动 90 天内共同关注、共同看多、共同看空或存在分歧的股票，并能进入详情查看账号、方向、理由与原帖。

对外仍定位为公开观点与市场信号追踪工具，不显示直接买卖建议。

## 1.2 报告结构

- 状态：`已确认`
- 责任方：前端

正式 Dashboard 调整为：

1. 顶部 10 个账号总览；
2. 日报；
3. 周报；
4. 季报，实际口径为滚动近 90 天；
5. 股票详情；
6. 账号个人视角。

季报必须显示实际起止日期，不能用不足 90 天的数据冒充完整季报。

## 1.3 日报栏目

- 状态：`已确认`
- 责任方：前端；数据字段由后端提供

日报按股票聚合，不按原帖堆叠。分为三个板块：

1. 明确共同看多；
2. 存在多空分歧；
3. 其他值得关注。

“其他值得关注”进入条件：

- 当天至少 3 个账号共同提及；或
- 某一个账号当天对同一股票发布至少 3 条去重原帖。

日报使用双列股票卡片，一行两个卡片。每张卡必须优先展示结论、账号头像、方向、理由和涨跌，减少正文。

## 1.4 周报定位

- 状态：`已确认`
- 责任方：前端

周报回答“这一周 10 个账号集中讨论什么”，重点展示：

- 本周讨论热度最高；
- 本周共同看多最多；
- 本周分歧最大；
- 相比前一周明显升温或方向变化的股票。

## 1.5 季报定位

- 状态：`已确认`
- 责任方：前端；时间窗口和聚合由后端支持

季报是滚动 90 天的聚合信息池，主要字段：

- 股票；
- 去重原帖数；
- 涉及账号数；
- 看多信号数或账号数；
- 看空信号数或账号数；
- 中性观点；
- 区间涨跌；
- 主要参与账号。

当前数据库最新日期为 2026-07-11，对应滚动 90 天范围为 2026-04-13 至 2026-07-11。

# 3. 10 个账号统一参与统计

## 3.1 统计原则

- 状态：`已确认`
- 责任方：后端提供结构化字段；前端展示

10 个账号全部参与“关注度”和“方向信号”统计，但方向依据随账号类型不同：

| 账号类型 | 看多依据 | 看空依据 |
|---|---|---|
| opinion | 本人明确看多 | 本人明确看空 |
| flow | 偏多期权流 | 偏空期权流 |
| news | 明确正面催化 | 明确负面催化 |
| disclosure | 买入披露 | 卖出披露 |

详情中必须标明方向依据，不能把期权流、新闻或披露伪装成账号本人的投资观点。

## 3.2 统一状态定义

- 状态：`已确认`
- 责任方：后端

建议正式统一为：

```text
bullish       看多信号
bearish       看空信号
neutral_view  明确中性观点
no_direction  无明确方向
mixed         同一窗口存在有效多空信号
```

定义：

- `neutral_view`：账号明确讨论该股票，但没有形成净多空方向或态度复杂；
- `no_direction`：背景提及、比较、引用、一般新闻或方向不足；
- `mixed`：同一账号、股票和统计窗口内同时存在有效看多与看空信号。

## 5.4 结构化短理由字段检查

- 状态：`已确认，字段已存在但命名需统一`
- 检查日期：2026-07-16
- 责任方：后端明确接口；前端按原字段展示

当前 `extract-v2` 没有独立的 `reason_short`、`short_reason` 或 `signal_reason` 字段，但已经在每条账号—股票记录中输出 `reasons[]`。提示词明确要求它是“账号本人陈述理由的短语数组”，没有理由时留空，禁止模型补写。`build_db.py` 将该数组原样写入股票数据库每条 `mentions[]`，并保留同一条记录的原帖正文和 URL，因此它是当前最接近“短理由”且可追溯的正式字段。

抽样检查 `zephyr_z9/extracted.json`：124 条非空理由，平均约 44 个字符，最长 99 个字符。说明大多数理由适合卡片摘要，但仍有部分会超过一级页面一行可视长度。前端可以截断显示并在展开层展示完整 `reasons[]`，不得自行改写；如果产品要求所有一级页面理由都严格控制长度，应由后端新增统一的 `signal_reason_short` 并保留原 `reasons[]`。

数据库另有股票级 `thesis_summary`，它来自 `ticker_map.json` 的人工/编辑性元数据，不是逐帖抽取字段，也不与单条原帖一一绑定，因此不能代替人物观点卡和原帖证据中的短理由。

验收标准：任一短理由都能从股票 `mentions[]` 回溯到同一记录的 `blogger_id`、`date`、`stance`、`text` 和 `url`；前端不从长原文临时生成理由。

### 理由字段统一使用规则

- 状态：`已确认`
- 确认日期：2026-07-16
- 责任方：前端 / 渲染脚本

Dashboard 一级页面、人物侧栏、日报、周报、季报、股票下钻和人物下钻中，所有标注为“理由”“观点理由”“信号理由”的内容统一读取对应结构化记录的 `reasons[]`。

禁止使用以下内容替代正式理由：

- 原帖正文 `text` 的前若干字符；
- 股票级编辑字段 `thesis_summary`；
- 前端自行总结、翻译或改写的文案；
- 与当前人物、股票或原帖记录无法一一对应的通用理由。

展示规则：保留 `reasons[]` 原语言和完整内容；空间不足时仅由 UI 折叠或截断，展开后恢复完整字段；每条理由必须与同一条 `mention` 的人物、股票、立场、日期和 `url` 绑定。`reasons[]` 为空时显示“原帖未提取出明确理由”或不展示理由区，不得从正文临时补写。
